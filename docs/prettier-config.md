# Prettier Configuration (issue #42)

Prettier is the project's one and only code formatter. It handles every file
type the repo has (Svelte components, TypeScript, CSS, Markdown, JSON with
exceptions — see below) so style debates never block a PR.

## Where the configuration lives

- `prettier.config.js` — the project config (see `Prettier's Rules` below).
- `.prettierignore` — files Prettier must never reformat.
- `prettier` and `prettier-plugin-svelte` in `devDependencies`.

The config was generated by the Svelte CLI (`npx sv create --add prettier`)
and extended for this repo.

## Prettier's rules

| Option          | Value                           | Effect                                          |
| --------------- | ------------------------------- | ----------------------------------------------- |
| `useTabs`       | `true`                          | Indent with tabs, not spaces                    |
| `singleQuote`   | `true`                          | `'string'` instead of `"string"`                |
| `semi`          | `false`                         | No semicolons at the end of statements          |
| `trailingComma` | `all`                           | Trailing commas in multi-line lists             |
| `printWidth`    | `100`                           | Wrap lines at 100 characters                    |
| `plugins`       | `prettier-plugin-svelte`        | Parse `.svelte` files through the Svelte plugin |
| `overrides`     | `*.svelte` → `parser: 'svelte'` | Force the Svelte parser for `.svelte` files     |

## Ignored files

`.prettierignore` keeps Prettier away from files it has no business touching:

- Package-manager lockfiles (`package-lock.json`, `pnpm-lock.yaml`, …)
- `/static/` — hand-tuned assets
- `/db/migrations/` — Drizzle-generated migration SQL and `meta/*.json`
  snapshots. These are regenerated by `npm run db:generate`, never hand-edited,
  so formatting them only adds noise to every migration diff.

Pro tip: an individual line can be opted out with a leading `prettier-ignore`
comment on its own line immediately above it:

```js
// prettier-ignore
const matrix = [[1, 0, 0], [0, 1, 0], [0, 0, 1]]
```

## Running it

```bash
npm run format   # prettier --write .   reformats everything in place
npm run lint     # prettier --check . && eslint .   CI-style check
```

`npm run lint` is the gate CI/reviewers care about; it fails if any file is
unformatted _or_ fails ESLint (see `docs/eslint-config.md`).

Editing workflow: write code in your editor, run `npm run format` (or an
on-save VSCode formatter), and commit. VSCode users get a one-click setup —
`esbenp.prettier-vscode` is already in `.vscode/extensions.json`.

## Changing the rules

Edit `prettier.config.js` and re-run `npm run format`. Two gotchas:

1. **ESLint must not fight it.** `eslint-config-prettier` is wired into
   `eslint.config.js` so the two tools never disagree. If you change a
   Prettier option that overlaps an ESLint formatting rule, Prettier wins.
2. **Re-format everything** after a config change (`npm run format`) so the
   whole repo stays on one convention, or the next commit will embed a
   half-reformatted diff.

## Verify

- `npm run lint` passes — it prints `All matched files use Prettier code style!`
  before handing over to the ESLint half of the gate.
- `git status` shows no `db/migrations/` files touched by a format run.
- The files in `docs/` are themselves Prettier-formatted (Prettier is not
  excluded there — this doc included).
